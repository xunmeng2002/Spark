# Logger 写路径重构计划：每线程块 ＋ 块级交接

本文记录 `WriteLog` 热路径去全局锁的方案与实施顺序。目标是把"每写一行取一次全局互斥锁"改为"每线程独占一块、满块才交接"，
同时保持现有日志语义：不丢数据、单线程内行序不变、单行不跨块。

## 现状

- `WriteLog` 宏 → `Logger::Write` → `WriteToLog`：先把行格式化进线程本地 64 KB `LogBuffer`。
- 取 `LogData::Mutex`，向全局 `CurrBuffer`（1 MB `LinearBuffer`）追加；空间不足时 `PushBuffer()` 分配新块并入队。
- `notify_one`、`ObjectPool` 分配、链表节点插入全部发生在临界区内。
- 代价：每行一次全局锁；多线程并发时同一把锁与同一块缓存行反复争用，是写路径的主要瓶颈。

## 备选方案与否决理由

| 方案 | 内容 | 结论 |
| :--- | :--- | :--- |
| A | notify 移出锁、预分配备用块、批量追加 | 低风险退路，但仍是一行一锁，未解决争用 |
| B1 | 每线程攒满 1 MB 才入队 | 低速率线程的数据会长期滞留，直到整块写满才可见 |
| B2 | 每线程 SPSC 字节环 | 环满时只能丢弃或阻塞，违背不丢日志；掉头写使实现复杂且易错 |
| C | 原子写指针预留空间 | 消费端可能读到尚未写完的区域，无锁语义不成立 |
| B3 | 每线程块 ＋ 块级交接 | 采用 |

## B3 结构

每个写过日志的线程持有自己的写入器；写入器独占一块 1 MB 缓冲。消费者（日志线程）在需要时把"非空块"整体取走，
写入器随后分配新块继续写。跨线程只交接**整块**，块内的行天然连续。

```cpp
struct LogThreadWriter
{
    std::mutex ChunkMutex;                            // 只保护块指针、满块队列与块内追加
    LinearBuffer<LogBufferSize>* Chunk = nullptr;     // 当前正在写的块，交接后置空
    std::list<LinearBuffer<LogBufferSize>*> FullChunks;  // 已写满、待消费者取走；顺序先于 Chunk
};

struct LogData
{
    std::uint64_t Generation;                         // 单调递增的代号，用于识别 TLS 中的旧写入器
    FILE* LogFile;
    std::list<std::unique_ptr<LogThreadWriter>> Writers;   // LogData 拥有写入器
    std::list<LinearBuffer<LogBufferSize>*> LogBuffers;    // 已交接、待落盘
    std::list<LinearBuffer<LogBufferSize>*> InnerLogBuffers;
    std::mutex Mutex;
    std::condition_variable ConditionVariable;
};
```

### 写入路径

1. 行照旧格式化进线程本地 `LogBuffer`。
2. 取本线程写入器（首次写入时注册；若 TLS 代号不是当前 `LogData::Generation`，按新一代重新注册）。
3. 在写入器本地锁内：块为空则分配；一行放不下就把旧块压入本线程的 `FullChunks` 再换新块；追加整行。
4. 写者全程不取全局锁；`FullChunks` 与当前块都由消费者取走，满块因此不会插到新块之后。
5. 只在**块由空变非空**与**满块换新**时 `notify_one`（每个交接周期一次）；消费者本就按 `ChunkHandOffInterval` 定时来取块。

> **注意**：满块不能"释放本地锁后自己入全局队列"——那会与消费者取走新块竞争，造成同一线程的行跨块重排。
> 满块先留在写入器本地队列，由消费者在**同一把本地锁内**按 `FullChunks` → `Chunk` 的顺序取出。

### 消费与交接

- 消费者每轮先取 `LogData::Mutex`，遍历 `Writers`，逐个取写入器本地锁，按 `FullChunks` → 当前块的顺序移入 `LogBuffers`。
- 满块随到随取；**未写满的小块只在攒够 `ChunkHandOffInterval = 20 ms` 后才取**。间隔的作用是把交接变成批量
  `fwrite`/`fflush`，避免低速率写者把交接退化成逐行 IO。（该间隔最初还为一件事而设：`LinearBuffer` 构造曾把
  1 MB 缓冲清零，每次交接都付一次 `memset`，实测让单线程 10 万行从 0.09 s 退化到 2.4 s；清零已按用户裁定去掉，
  见 `docs` 与台账，间隔保留的只是批量落盘这一条理由。）
- 随后按现有逻辑交换列表、`fwrite`、`fflush`；没有块可写时睡到"最早一块到期"的时刻（没有待成熟块则睡 1 秒），
  因此空闲时与原先一样每秒醒一次，有待成熟块时按到期时刻精确唤醒。
- 停止/退出路径（`FlushRemainingBuffers`、写入器注销）无条件取走未成熟小块，不因间隔而丢数据。
- 线程退出：先取本地锁拿走剩余块（含 `FullChunks`），再取全局锁注销写入器并按序入队，最后唤醒消费者。
- `Stop`/`Join`：`FlushRemainingBuffers` 先取走所有写入器的剩余块，再落盘。

### 锁序

- 消费者：全局锁 → 写入器本地锁。
- 写者：只持本地锁追加，从不取全局锁。
- 线程退出：先取本地锁拿走块并释放，再取全局锁注销（不嵌套）。

因此不存在"写者持本地锁等全局锁、消费者持全局锁等本地锁"的环。

### 生命周期

- `LogData` 用 `unique_ptr` 拥有写入器；TLS 只保存非拥有指针与代号。
- 代号必须单调递增，**不能比较 `LogData` 地址**：停止后重新 `Init` 时，分配器极易复用同一地址，
  地址相同会让 TLS 拿到已释放的写入器（实测可复现崩溃）。
- 停止时先置"日志器存活"标志为假，再销毁 `LogData`；此后 TLS 析构只清零指针，不解引用已销毁对象。
- 重新 `Init` 后，旧 TLS 的代号与新 `LogData` 不匹配，写入时重新注册，不复用悬空对象。
- 停止后的写入沿用现状：静默丢弃。

### 排序与语义

- 单线程内行序不变；块内连续，块按交接顺序落盘。
- 跨线程不再按行全局串行，改为**按块交错**（已确认）。
- 不丢数据：块满即进入本线程待取队列，消费者按序取走；内存占用与今天同属无上限，积压时表现为块数增长，不静默丢行。

### 单行上限

- 单行格式化结果上限 `LogLineLength = 64 KB`，块为 1 MB，单行始终能整行落进一个空块。
- 行绝不跨块：跨块会让其他线程的块插进同一行中间，破坏行完整性。
- 编译期约束：`static_assert(LogBufferSize >= LogLineLength, "一条日志必须整行落进一个块")`。

## 分阶段落地

1. 数据结构：`LogThreadWriter`、`LogData::Writers`，去掉 `CurrBuffer`。
2. 写入路径：本地块追加 ＋ 满块交接；行为与输出格式不变。
3. 消费与退出：取块、注销、`Stop/Join` 收尾。
4. 测试与基准：多线程正确性用例；记录改造前后吞吐对比。

## 测试与验收

- 4 线程各写 N 行：行数完整，每线程序号严格递增；行不粘连、不截断。
- 单条 70 000 字符超长行：截断到上限，前后行完整，下一行可正常写入。
- 线程写一行后立即退出：该行必须落盘。
- 停止时仍有活跃写线程：停止前已完成的写入不丢。
- 停止后写入：不崩溃、不产生新文件内容。
- 不满一块的行在运行期（未 `Stop`）也必须出现在日志文件里：写入后 3 秒内能看到。
- 基准：多线程写入吞吐不低于改造前；单线程不出现明显回退。

## 基准（2026-10-29 实测）

方法：同一份基准源码（4 行短日志，`cl /O2 /DNDEBUG`），分别与 HEAD（`fc5e7bd`）的 Logger 源码和重构后的源码一起编译，
交替各跑 5 次取区间；指标为"写完最后一行"的耗时（不含进程启动与最终落盘）。日志文件逐行核对，行数不丢。

| 场景 | 改造前（HEAD） | 改造后 | 倍数 |
| :--- | :--- | :--- | :--- |
| 1 线程 × 10 万行 | 0.98 ~ 1.13 s（约 9.5 万行/s） | 0.09 ~ 0.13 s（约 100 万行/s） | 约 10× |
| 4 线程 × 10 万行 | 3.4 ~ 4.4 s（约 9 ~ 12 万行/s） | 0.10 ~ 0.16 s（约 250 ~ 410 万行/s） | 约 30 ~ 40× |
| 8 线程 × 5 万行 | 1.1 ~ 1.4 s（约 29 ~ 35 万行/s） | 0.07 ~ 0.08 s（约 510 ~ 570 万行/s） | 约 18× |

未加 `ChunkHandOffInterval` 时，单线程实测反而退化到 2.4 s——当时的原因是每次交接都触发一次 1 MB 缓冲的清零，
该清零随后已去掉（`LinearBuffer` 构造不再 `buffer_{0}`，1 MB 缓冲反复分配/回收由约 14 µs/次降到约 10 ns/次）。
耗时随线程数线性下降，说明写路径已基本不再串行。

## 风险

- **停止竞态**：线程在 `LogData` 销毁后仍写入属未定义用法，与今天相同；新增的只是 TLS 析构安全检查。
- **内存积压**：不做背压，积压时块数增长，与今天一致。
- **唤醒频率**（`8b123ec` 起）：只在块开头与换新时通知。原先每行通知，实测单写者 50 万行时日志线程被按行唤醒、几乎占满一个核
  （进程 CPU 0.45 s / 墙钟 0.21 s ＝ 2.1 核，而进程只有 2 个线程）；降频后 CPU 0.25 s、墙钟 157 ms。
  残余风险：通知可能落在"消费者尚未登记为等待者"的几百纳秒缝里而丢失，最坏退化为等一个 1 s 空闲兜底——不丢数据，
  且写入速率超过约 1.1 万行/秒时 1 MB 块会先写满并触发换块通知自愈。收掉它可把兜底降到 `ChunkHandOffInterval`。
- **小块延迟**：未写满的块最迟等 `ChunkHandOffInterval = 20 ms` 才交接，安静下来的写线程最后几行最多晚 20 ms 落盘
  （停止时无条件落盘，不受此限）。Windows 上定时等待受 15.625 ms 系统节拍约束，实测这一期限实际在约 31.5 ms 兑现。
- **小块利用率**：低速率写者的块可能只装了很少就交接（1% 量级）；去掉清零后这不再有 CPU 代价，但日志线程被拖慢时，
  同样多的积压数据会占更多块内存（最坏每 20 ms 一块）。真遇到内存上涨，先调大 `ChunkHandOffInterval`。
- **缓存行**：写入器结构体按线程独立，跨线程只争用全局锁交接口。

## 决策记录

2026-10-29 确认：

- 块大小 1 MB。
- 每行写入后通知消费者（沿用现状）。
- 跨线程允许按块交错，不保证全局行序。
- 块满不丢弃：交接入队，由消费者落盘。
- 单行不跨块，并以 `static_assert` 固定该不变量。

2026-10-29 追加（基准实测后）：

- 小块交接加 20 ms 间隔（`ChunkHandOffInterval`）。原设计中消费者每轮无条件取走当前块，写者随即重新分配并清零 1 MB，
  交接次数随唤醒次数增长，单线程基准反而退化到改造前的 2.4 倍耗时；加间隔后恢复并大幅超过改造前。
  语义不变：满块随到随取、停止/退出无条件取走、单线程内行序不变。

2026-10-29 追加（用户裁定）：

- `LinearBuffer<Size>` 构造不再把缓冲清零（`buffer_{0}` 是保守写法）。使用方一律按 `GetLength()` 取数据，
  未写入的字节从不被读取；1 MB 缓冲反复分配/回收的成本由约 14 µs/次降到约 10 ns/次。
  交接间隔 20 ms 因而只剩"批量落盘"这一条理由，保留不变。
