# clang-format 与 `rules/cpp-style.md` §4 的对应关系

仓库根目录新增 `.clang-format`，把 §4「类内顺序」中**能被格式化工具表达**的那一半固化下来。
本文说明覆盖边界、验证方式，以及无法用 clang-format 表达时的替代手段。

---

## 1. 结论速览

| §4 条款 | clang-format 能否表达 | 手段 |
| :--- | :--- | :--- |
| 标签顶格 | ✅ | `AccessModifierOffset: -4`（相对成员再左移 4 列，与 `class` 同列） |
| 成员缩进 4 空格 | ✅ | `IndentWidth: 4` + `IndentAccessModifiers: false` |
| 段间空行 | ✅ | `EmptyLineBeforeAccessModifier: LogicalBlock` |
| Allman 括号 | ✅ | `BreakBeforeBraces: Allman` |
| 访问段优先 `public` → `protected` → `private` | ❌ | 结构检查脚本（见 §3.1） |
| 段内 6 组序（类型别名 → 常量 → 特殊成员 → 其他操作符 → 普通函数 → 数据成员） | ❌ | 结构检查脚本（见 §3.1） |
| 数据成员置于段末 | ❌ | 结构检查脚本（见 §3.1） |
| 每段尽量只出现一次（不重复开标签） | ❌ | 结构检查脚本（见 §3.1） |
| 显式写访问标签，不依赖 `class` 默认私有 | ❌ | 结构检查脚本（见 §3.1） |
| 非静态数据成员声明顺序 → 初始化列表一致 | ❌ | 检查脚本 + 编译器警告 `-Wreorder`（双保险，见 §3.1 / §3.2） |
| 段内子组之间的空行（如常量与特殊成员之间） | ❌ | 手工；`EmptyLineBeforeAccessModifier` 只管访问标签，不管段内分组 |

---

## 2. 可表达部分的实测验证

**正例**：把 §4 规范里的 `Example` 示例去掉缩进后交给 clang-format，
输出与规范原文逐字一致——标签顶格、成员缩进 4 空格、`public`/`protected`/`private`
三段之间有且仅有一个空行，且 `{` 之后的首个标签上方**不**补空行（`LogicalBlock` 的行为）。

**反例（证明边界）**：构造一个同时含四类违规的类——

- 数据成员出现在构造函数之前；
- 数据成员未置于段末；
- `public:` 重复出现两次；
- `private:` 出现在 `protected:` 之前；
- 初始化列表顺序与声明顺序相反。

`clang-format --style=file` 的输出与输入**零差异**。即这五类问题 clang-format 一律不管，
不能指望它兜底。

## 3. 不可表达部分的替代手段

### 3.1 结构性问题用检查脚本

`tools/` 下的两个脚本覆盖上表**全部** ❌ 结构项：

| 脚本 | 覆盖条款 |
| :--- | :--- |
| `tools/s4scan.py` | 标签顶格 / 段间空行 / 访问段优先级 / 段内 6 组序 / 数据成员置段末 / 每段只出现一次 / 显式首标签 |
| `tools/initcheck.py` | 非静态数据成员声明顺序与初始化列表一致 |

两个脚本都是「只读扫描 + 报告」，不修改文件；且都以「注入的已知正例必须报警、已知反例必须不报警」
做过判别力验证，避免出现「0 命中」其实是判据失灵的情况。语料入库在 `tools/selfcheck/`，
可照抄命令复现——只报「0 命中」而不先自证判别力的扫描器，其绿灯不具意义。
用法与判据细节见 `tools/README.md`。

### 3.2 初始化列表顺序另有编译器警告兜底

脚本之外，同一条款还有编译器侧的第二道防线（二者互补：脚本查得出、警告查得准）：

- GCC / Clang：`-Wreorder`
- MSVC：`C5038`（`/W4` 起）

**注意**：`-Wreorder` **不在** GCC/Clang 的默认告警集内（含在 `-Wall` 中，但本仓库未开 `-Wall`），
必须在顶层 `CMakeLists.txt` 显式打开。本仓库已按「只加这一条、不带其它警告」的最小改动落地：

```cmake
if(NOT MSVC)
    add_compile_options(-Wreorder)
endif()
```

MSVC 侧未启用：`C5038` 属 `/W4` 级，本项目未开 `/W4`，单独用 `/w15038` 亦需要
在 Windows 工具链上实测确认，故留待有可用 MSVC 环境的时机再评估。

## 4. 全仓收敛过程与判据（已完成）

手写代码现已全部满足本配置：`clang-format --dry-run --Werror` 在 **167/167** 个手写文件
上通过。另有 9 个生成物 + 14 个第三方快照 + 10 个判别力语料**按设计不纳入检查**，见 §4.1。

### 4.1 范围：只收敛手写文件

| 类别 | 文件数 | 处理 |
| :--- | ---: | :--- |
| 手写 | 167 | 全部收敛，纳入 `--Werror` |
| 生成物（带「请勿手改 / 自动生成」标记） | 9 | **不碰**。改了会被下次 pump 静默回滚，要改得改仓库外的模板 |
| 第三方 `Serialization/json/` 两份快照 | 14 | **不碰**。与上游一致比统一缩进重要 |
| 判别力语料 `tools/selfcheck/` | 10 | **不碰**。那里是**故意写坏**的语料，且靠自带 `.clang-format`（`DisableFormat: true`）挡住格式化 |

全仓 `.h`/`.cpp` 共 200 个，正好是 167 + 9 + 14 + 10。

> **注意一处已更正的数字**：本节原先写的是「173/173」。173 **复现不出来**，它是「167 手写 +
> `e5a27cb`（2026-09-17）当时 `tools/selfcheck/` 下的 **6** 个 `.h`/`.cpp 语料」——即那次计数
> 把判别力语料一起数了进去，而文件筛选**排除**该目录是之后才加的。更值得留意的是那 6 个文件
> 当时是**空过**的：`tools/selfcheck/.clang-format` 设了 `DisableFormat: true`，clang-format 对
> 它们不检查、自然无违规。**「N/N 全绿」里的 N 一旦口径变了，绿灯的含义就跟着变，而报告里只留下
> 一个数字。** 复核时请连同文件筛选口径一起看。今日 10 个语料 + 167 手写 = 177，与 173 无关。


### 4.2 三步走与实测数字

| 提交 | 内容 | 文件数 | 可豁免 blame |
| :--- | :--- | ---: | :--- |
| `030f614` | Tab 按制表位（`TabWidth: 4`）展开为空格 | 109 | 是 |
| `9539b25` | A 步：空白与换行布局归一，**不改变任何字符** | 142 | 是 |
| `0ff2111` | B 步：含字符增删的收尾 | 4 | **否**，必须留在 blame 里 |

`030f614` 选「按制表位展开」而非「粗换 4 空格」：本仓 Tab 大量用于续行对齐，粗换会把
每条对齐的续行错开，那就不是机械归一化而是重新排版了。

A 步与 B 步的**分界判据**是「去掉全部空白（含换行）后内容是否逐字相同」——A 步满足，
故一个字符都没改；B 步不满足，含真实字符增删，其中最典型的是 `Logger.h` 的
`WriteErrorLog` 宏续行被重折、**多出一个续行反斜杠**。把 B 步单独分出来的唯一目的，就是
不让这类改动混进 A 步而随之一并被 blame 豁免——那等于把真实改动藏起来。

**注意一处易错的归类**：初始化列表的 `:member` -> `: member` 属于**空白**改动（冒号后
加空格），归 A 步，不是真实字符变化。曾把它当「含非空白」记进文档，是错的。

### 4.3 两个量法与判据上的坑（都踩过）

**坑 1：别用 `zip(a, b)` 逐行对位。** 两侧行数不等时，第一个插入点之后**每一行都会被
判成「改了」**。实测把 863 行夸成 5241 行，并凭空造出「大括号挂行」这种本配置
（`BreakBeforeBraces: Allman`）下不可能出现的假象。须用 LCS 对位，并拿
`git diff --no-index --numstat` 复核（两者应逐行吻合）。

**坑 2：别用「`git diff -w` 为空」当纯空白证明。** clang-format 会把一行拆成两行，例如
`std::thread producer([&]()` 被拆成 `std::thread producer(` + `[&]()`——内容相同但行结构
变了，`-w` 照样报。要证明「不改变任何字符」，正确判据是「去掉全部空白（含换行）后逐字
相同」，它比 `-w` 弱但确实成立；反之若声称 `-w` 为空，须先确认没有重折行。

### 4.4 收敛后的既定事实

- 初始化列表的 `:` 后空格：clang-format 固定输出 `: member(`，**无开关可关**。仓库现已
  全部改为该写法。
- 短函数并成单行、超长签名按代价模型重折：同上，无开关，已按配置生效。
- 生成物仍保留 Tab 与旧缩进——**这是刻意的**，要改须改仓库外的模板。

### 4.5 格式化会改掉被检对象的**写法**，检查器与语料都得跟着动

收敛完成后复核工具，`tools/initcheck.py` 的通道 B 由 **217 掉到 211**。原因不在工具，
也不在格式化本身，而在两者的**接缝**：clang-format 把较短的类外初始化列表并到签名行、
`{` 留在次行（Allman）——

```cpp
Timer::Timer() : timeInterval_(60000), eventCount_(600), currentEventCount_(0)
{
```

而通道 B 的旧判据要求 `:` 与 `{` 同行，于是这类定义整条**静默脱离检查**。数字变小了，
但没有任何东西报错。

**「0 命中」的自证这次也没兜住**：`tools/selfcheck/` 里通道 B 只有 `initpos.cpp` 一条语料，
用的恰是**新旧判据都能认**的「`:` 独占一行」形状——判据失效期间自检全绿。
补充三份语料（见 `tools/selfcheck/README.md` 的「形状覆盖」），并对三个历史错判据实测了
判别力矩阵，确认三份各钉住一类、缺一份就漏一类。

最终判据不再按形状分支，而是**贴合语法**：括号外的 `{`，左侧跳空白后紧贴标识符或 `>`/`]`
的是成员 braced-init，其余（前接 `)` 或处在行首）是函数体起点。这一步踩了两次坑——
「第一个 `{` 即函数体」会把 `buff_{0}` 当成函数体而截断列表，「配对 `}` 同行算 braced-init」
又会被空函数体 `{}` 骗过、越过函数体继续往后扫。两次都是**先写出一个看似合理的形状判据，
再用语料逼出反例**才发现。

> **可推广的一条**：格式化工具改变的是**被检对象的写法**，而检查器与判别力语料都是按写法
> 写的。全仓格式化之后，**所有按书写形状下判据的检查器都要复核一遍口径**，语料也要补上
> 新形状——否则会出现「代码更规范了，检查反而更少了」这种没有任何信号的结果。

## 5. 用法

只检查、不改文件：

```bash
clang-format --style=file --dry-run --Werror <files...>
```

**自 §4 收敛之后，手写文件上这条命令应为全绿**，可以直接当门禁用（167/167 通过）。
但文件筛选那步**必须先排除** 9 个生成物与 14 个第三方快照，否则门禁从启用当天就是红的
——它们是刻意不收敛的，见 §4.1。`tools/selfcheck/` 同理，且它另有一层原因：那里是
故意写坏的判别力语料（见 §3.1 与 `tools/README.md`）。

格式化单个文件（改前先看 diff）：

```bash
clang-format --style=file path/to/File.h > /tmp/new.h
diff -u path/to/File.h /tmp/new.h
```

**改前务必确认待格式化的文件不在两个排除清单里**，尤其别对生成物跑 `-i`：改动会被下次
pump 静默回滚，等于白改且白白制造一次 churn。

## 6. 默认值审计：没写进配置的项并不安全

`BreakTemplateDeclarations` 与 `AlignEscapedNewlines` 这两处默认值覆盖作者写法，暴露的是同一个
结构问题：**配置里"没写"不等于"没有规定"**，而是"由 LLVM 默认值规定"——而默认值随
clang-format 版本变。每一次升级都可能静默重排全仓，且**没有任何信号**：文件能编过、测试全绿、
连"纯空白改动"的判据都拦不住（template 并行的那 31 处就是按字符判据归进 A 步的，因为它确实
只动了空白）。

所以要问的不是"要不要写这一项"，而是"这一项现在是谁在定"。审计方法：

```bash
clang-format --style=file --dump-config > resolved.txt
clang-format --style=LLVM --dump-config > llvm.txt
```

两个 dump 各自解析成键值对，与 `.clang-format` 的显式键做**三方对比**：显式键 / 本配置解析值 /
LLVM 默认值。三者一致 = 显式记账；显式缺失但两侧一致 = **骑默认**（风险项）。

### 6.1 一个会读错格式的坑

`--dump-config` 里**空值不代表空**，而是一个**嵌套结构**，其子项另起缩进行给出。例如：

```yaml
AlignTrailingComments:
  Kind: Always
  OverEmptyLines: 0
```

把这一项读成标量、写进配置成 `AlignTrailingComments: Never`，语义就从"默认对齐"变成"显式取消
对齐"——直接改掉 `MD5.cpp`、`TcpIocpConnect.h` 里已有的行尾注释对齐。**这个错误实测踩过一次**，
靠"改了配置之后受影响的文件数从 16 变 18"才发现。凡 dump 出空值的项，都必须往下读它的子项。

### 6.2 审计结论

显式键 92 项（`§3`/`§4` 段 24 + `§5` 段 68），其余 128 项骑在 LLVM 默认值上；其中 39 项与
C++ 代码输出相关，逐项实测后分四类：

| 类 | 项数 | 含义 | 处置 |
| :--- | ---: | :--- | :--- |
| A | 3 | 默认值**覆盖了作者原有写法** | 改默认值，见 `.clang-format` 5.1 |
| B | 32 | 默认值与作者写法**一致** | 显式钉死，见 5.2–5.6 |
| C | 4 | 作者两种写法**各占一半**，无多数派 | 逐项裁定 |
| 其余 | 26 | 本仓未涉及该特性（概念约束、汇编、`requires` 等） | 不动 |

A 类三项即 §4.5 与 5.1 记录的：`BreakTemplateDeclarations`（31 处被并行）、`AlignEscapedNewlines`
（4 行宏续行被补 91~110 个空格，进而触发重折、多出一个续行反斜杠）、`SpaceAfterTemplateKeyword`
（默认 `true` 与作者 63 处中 48 处的写法一致，属"归并到多数派"而非覆盖，故维持）。

C 类四项——`AlignConsecutiveMacros`、`Cpp11BracedListStyle`、`BreakConstructorInitializers`、
`PackConstructorInitializers`——两种写法在仓里各占约一半，**没有"作者原意"可还原**，属真正的
风格选择，按与 `.editorconfig` 及 §3 其它条款的一致性裁定。

### 6.3 判"哪一边才是作者原意"的度量要求

要证明"默认值覆盖了作者写法"，就得比出格式化**前**的写法偏向哪边。两个坑：

- **距离度量必须含字符级项。** 只看行数差是瞎的：`template<int` 与 `template <int` 行数相同，
  在纯行数度量下距离为零。
- **两侧行数不等时不能用 `zip(a, b)` 逐行对位**（同 §4.3 坑 1）。须用 LCS 对位，再对每个对齐
  对累加"长度差 + 不同字符数"。

## 7. `§5` 记录性钉死：清单与维护约定

`.clang-format` 的 `§5` 段（68 项）**不是新的风格决定，是记账**：把当前生效值写下来，使"这一项
是谁定的"在配置文件里有迹可循，而不是隐式依赖某个版本的默认值。**每一项都实测确认过：写进去
之后全仓输出逐字不变。**

### 7.1 两处"看起来该写、写错更糟"的项

| 项 | 陷阱 |
| :--- | :--- |
| `AlignConsecutiveBitFields` / `Declarations` / `Macros` | 简写 `None` **不等于**默认值：它会把子项 `PadOperators` 隐式置成 `true`，而这三项的默认是 `false`。本仓未启用这些对齐，输出上看不出差别，但**配置已与默认值不同**。故这三项**刻意不写**，保持骑默认 |
| `AlignTrailingComments` | 默认是嵌套结构 `Kind: Always`，不是标量。写成 `Never` 会取消已有对齐（见 §6.1） |

`AlignConsecutiveAssignments` 是例外：它的 `PadOperators` 默认本就是 `true`，所以只有它写
`None` 与默认值等价（实测通过）。规则是**写错值比不写更糟**——这一类项要先 dump 子项再决定。

### 7.2 刻意不写的一项

`LineEnding` 保持不指定（解析为 `DeriveLF`）。行尾符属于**文件编码**约定而非风格决定，写死成
`LF` 会让将来任何 CRLF 文件被静默改行尾。此项归 `.editorconfig` 管。

### 7.3 维护约定

- **新增或修改 `§5` 任一项**，须同步改本节，并实测"全仓输出逐字不变"（或明确记录哪些文件变了、
  为什么）。
- **升级 clang-format 版本后**，重跑 §6 的三方对比。§5 的意义正在于此：钉死之后，新版本能影响
  的只剩未钉死的项，比对范围是可控的。
- **改动 `tools/` 下的检查器后**，先跑 `tools/selfcheck/` 的判别力自检（见 §3.1 与 `tools/README.md`），
  再相信它在真实代码上的数字。
