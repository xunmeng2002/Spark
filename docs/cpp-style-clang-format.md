# clang-format 与 `rules/cpp-style.md` §4 的对应关系

仓库根目录新增 `.clang-format`，把 §4「类内顺序」中**能被格式化工具表达**的那一半固化下来。
本文说明覆盖边界、验证方式，以及无法用 clang-format 表达时的替代手段。

---

## 1. 结论速览

| §4 条款 | clang-format 能否表达 | 手段 |
| :--- | :--- | :--- |
| 标签顶格 | ✅ | `AccessModifierOffset: -4`（相对成员再左移 4 列，与 `class` 同列） |
| 成员缩进 4 空格 | ✅ | `IndentWidth: 4` + `IndentAccessModifiers: false` |
| 段间空行 | ✅ | `EmptyLineBeforeAccessModifier: LogicalBlock` |
| Allman 括号 | ✅ | `BreakBeforeBraces: Allman` |
| 访问段优先 `public` → `protected` → `private` | ❌ | 结构检查脚本（见 §3.1） |
| 段内 6 组序（类型别名 → 常量 → 特殊成员 → 其他操作符 → 普通函数 → 数据成员） | ❌ | 结构检查脚本（见 §3.1） |
| 数据成员置于段末 | ❌ | 结构检查脚本（见 §3.1） |
| 每段尽量只出现一次（不重复开标签） | ❌ | 结构检查脚本（见 §3.1） |
| 显式写访问标签，不依赖 `class` 默认私有 | ❌ | 结构检查脚本（见 §3.1） |
| 非静态数据成员声明顺序 → 初始化列表一致 | ❌ | 检查脚本 + 编译器警告 `-Wreorder`（双保险，见 §3.1 / §3.2） |
| 段内子组之间的空行（如常量与特殊成员之间） | ❌ | 手工；`EmptyLineBeforeAccessModifier` 只管访问标签，不管段内分组 |

---

## 2. 可表达部分的实测验证

**正例**：把 §4 规范里的 `Example` 示例去掉缩进后交给 clang-format，
输出与规范原文逐字一致——标签顶格、成员缩进 4 空格、`public`/`protected`/`private`
三段之间有且仅有一个空行，且 `{` 之后的首个标签上方**不**补空行（`LogicalBlock` 的行为）。

**反例（证明边界）**：构造一个同时含四类违规的类——

- 数据成员出现在构造函数之前；
- 数据成员未置于段末；
- `public:` 重复出现两次；
- `private:` 出现在 `protected:` 之前；
- 初始化列表顺序与声明顺序相反。

`clang-format --style=file` 的输出与输入**零差异**。即这五类问题 clang-format 一律不管，
不能指望它兜底。

## 3. 不可表达部分的替代手段

### 3.1 结构性问题用检查脚本

`tools/` 下的两个脚本覆盖上表**全部** ❌ 结构项：

| 脚本 | 覆盖条款 |
| :--- | :--- |
| `tools/s4scan.py` | 标签顶格 / 段间空行 / 访问段优先级 / 段内 6 组序 / 数据成员置段末 / 每段只出现一次 / 显式首标签 |
| `tools/initcheck.py` | 非静态数据成员声明顺序与初始化列表一致 |

两个脚本都是「只读扫描 + 报告」，不修改文件；且都以「注入的已知正例必须报警、已知反例必须不报警」
做过判别力验证，避免出现「0 命中」其实是判据失灵的情况。语料入库在 `tools/selfcheck/`，
可照抄命令复现——只报「0 命中」而不先自证判别力的扫描器，其绿灯不具意义。
用法与判据细节见 `tools/README.md`。

### 3.2 初始化列表顺序另有编译器警告兜底

脚本之外，同一条款还有编译器侧的第二道防线（二者互补：脚本查得出、警告查得准）：

- GCC / Clang：`-Wreorder`
- MSVC：`C5038`（`/W4` 起）

**注意**：`-Wreorder` **不在** GCC/Clang 的默认告警集内（含在 `-Wall` 中，但本仓库未开 `-Wall`），
必须在顶层 `CMakeLists.txt` 显式打开。本仓库已按「只加这一条、不带其它警告」的最小改动落地：

```cmake
if(NOT MSVC)
    add_compile_options(-Wreorder)
endif()
```

MSVC 侧未启用：`C5038` 属 `/W4` 级，本项目未开 `/W4`，单独用 `/w15038` 亦需要
在 Windows 工具链上实测确认，故留待有可用 MSVC 环境的时机再评估。

## 4. 全仓收敛过程与判据（已完成）

手写代码现已全部满足本配置：`clang-format --dry-run --Werror` 在 **173/173** 个手写文件
上通过。另有 9 个生成物 + 14 个第三方快照**按设计不纳入检查**，见 §4.1。

### 4.1 范围：只收敛手写文件

| 类别 | 文件数 | 处理 |
| :--- | ---: | :--- |
| 手写 | 173 | 全部收敛，纳入 `--Werror` |
| 生成物（带「请勿手改 / 自动生成」标记） | 9 | **不碰**。改了会被下次 pump 静默回滚，要改得改仓库外的模板 |
| 第三方 `Serialization/json/` 两份快照 | 14 | **不碰**。与上游一致比统一缩进重要 |

### 4.2 三步走与实测数字

| 提交 | 内容 | 文件数 | 可豁免 blame |
| :--- | :--- | ---: | :--- |
| `030f614` | Tab 按制表位（`TabWidth: 4`）展开为空格 | 109 | 是 |
| `9539b25` | A 步：空白与换行布局归一，**不改变任何字符** | 142 | 是 |
| `0ff2111` | B 步：含字符增删的收尾 | 4 | **否**，必须留在 blame 里 |

`030f614` 选「按制表位展开」而非「粗换 4 空格」：本仓 Tab 大量用于续行对齐，粗换会把
每条对齐的续行错开，那就不是机械归一化而是重新排版了。

A 步与 B 步的**分界判据**是「去掉全部空白（含换行）后内容是否逐字相同」——A 步满足，
故一个字符都没改；B 步不满足，含真实字符增删，其中最典型的是 `Logger.h` 的
`WriteErrorLog` 宏续行被重折、**多出一个续行反斜杠**。把 B 步单独分出来的唯一目的，就是
不让这类改动混进 A 步而随之一并被 blame 豁免——那等于把真实改动藏起来。

**注意一处易错的归类**：初始化列表的 `:member` -> `: member` 属于**空白**改动（冒号后
加空格），归 A 步，不是真实字符变化。曾把它当「含非空白」记进文档，是错的。

### 4.3 两个量法与判据上的坑（都踩过）

**坑 1：别用 `zip(a, b)` 逐行对位。** 两侧行数不等时，第一个插入点之后**每一行都会被
判成「改了」**。实测把 863 行夸成 5241 行，并凭空造出「大括号挂行」这种本配置
（`BreakBeforeBraces: Allman`）下不可能出现的假象。须用 LCS 对位，并拿
`git diff --no-index --numstat` 复核（两者应逐行吻合）。

**坑 2：别用「`git diff -w` 为空」当纯空白证明。** clang-format 会把一行拆成两行，例如
`std::thread producer([&]()` 被拆成 `std::thread producer(` + `[&]()`——内容相同但行结构
变了，`-w` 照样报。要证明「不改变任何字符」，正确判据是「去掉全部空白（含换行）后逐字
相同」，它比 `-w` 弱但确实成立；反之若声称 `-w` 为空，须先确认没有重折行。

### 4.4 收敛后的既定事实

- 初始化列表的 `:` 后空格：clang-format 固定输出 `: member(`，**无开关可关**。仓库现已
  全部改为该写法。
- 短函数并成单行、超长签名按代价模型重折：同上，无开关，已按配置生效。
- 生成物仍保留 Tab 与旧缩进——**这是刻意的**，要改须改仓库外的模板。

## 5. 用法

只检查、不改文件：

```bash
clang-format --style=file --dry-run --Werror <files...>
```

**自 §4 收敛之后，手写文件上这条命令应为全绿**，可以直接当门禁用（173/173 通过）。
但文件筛选那步**必须先排除** 9 个生成物与 14 个第三方快照，否则门禁从启用当天就是红的
——它们是刻意不收敛的，见 §4.1。`tools/selfcheck/` 同理，且它另有一层原因：那里是
故意写坏的判别力语料（见 §3.1 与 `tools/README.md`）。

格式化单个文件（改前先看 diff）：

```bash
clang-format --style=file path/to/File.h > /tmp/new.h
diff -u path/to/File.h /tmp/new.h
```

**改前务必确认待格式化的文件不在两个排除清单里**，尤其别对生成物跑 `-i`：改动会被下次
pump 静默回滚，等于白改且白白制造一次 churn。
